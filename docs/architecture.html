RockyWebDE · feasibility

A desktop that lives in a browser

Almost all of what you described is possible. But “a web app that looks and functions like a modern desktop environment” resolves into three genuinely different systems, and picking between them is the whole project.

Targets: Debian · RHEL · Fedora · Rocky Status: green field
The pivot

One decision determines everything downstream

Can you run GIMP in it? Does it work over a network? Do you have to write a Wayland compositor? Every one of those questions collapses into a single structural choice: where does the browser sandbox end and the native system begin?

The constraint that forces the choice is hard and permanent. A browser cannot host a native window. There is no API — not on X11, not on Wayland — that places a wl_surface or an X window inside a DOM node. Nothing on the roadmap will add one. So you have exactly three places to put the boundary: above the apps (stream their pixels into the page), below the shell (composite them natively, alongside your web UI), or nowhere at all (there are no native apps).

Those three placements are the three architectures below. They share almost no code.

Option one

Web-Native: no native apps at all

boundary at the bottom

The desktop is a web app, and so is everything in it

You build a shell in the browser — a panel, a launcher, workspaces, a window manager whose “windows” are absolutely-positioned DOM nodes. Everything running inside is either a first-party web app you wrote (file manager, terminal, settings, image viewer) or a third-party web app in an iframe. There is no Xwayland, no compositor, no streaming.

What you build with. Any modern framework for the shell; the window manager is a few thousand lines of your own code, not a library. xterm.js over a ttyd-style PTY WebSocket gives you a genuinely good terminal. WASM covers local compute. For anything that touches the system — mounting disks, managing services, reading logs, editing files with real permissions — use cockpit-bridge rather than writing a privileged daemon (see below).

What it costs. Nothing technically hard, and that is the tell: the difficulty is entirely in scope. You are re-implementing a desktop's worth of applications. And the honest framing is that this is not a Linux desktop — it is a web OS that happens to be hosted on Linux. Users who want LibreOffice do not get LibreOffice.

Precedent: Puter, daedalOS, anuraOS; ChromeOS before Crostini.

Verdict

Ships fastest, behaves identically on every distro, and is the only option with no native-integration surface to maintain. Choose it if the goal is a coherent product; reject it if the goal is to run existing Linux software.

Option two

Streamed: real apps, delivered as pixels

boundary in the middle

Native windows arrive in the page one canvas at a time

Applications run for real on the host, headless, under Xvfb or Xwayland. A streaming server captures them per window and ships encoded frames to the browser; your JavaScript shell receives each window as its own <canvas>, then positions, decorates, stacks and focuses it exactly as if it were a DOM window. Input travels back the other way. To the user it looks like one desktop.

Xpra’s seamless mode is the key primitive here and it already does the hard part: it forwards individual windows rather than a whole screen, and its HTML5 client keeps each forwarded window inside the browser canvas — which is precisely the arrangement you want, since it hands window placement to your shell instead of a remote WM. It also forwards clipboard, audio, notifications, printers and system trays.

Selkies is the performance option. GPU-accelerated capture and encode, WebSockets plus WebCodecs by default with WebRTC available as an opt-in transport, and roughly 60 fps at 1080p even with software encoding. It streams a full desktop rather than seamless windows, so it fits a “desktop in a tab” product better than a windowed shell. KasmVNC is the low-dependency fallback — simpler, no audio.

The strategic risk is X11. Xpra's seamless mode is an X11 technology, and Selkies' Wayland support is planned rather than shipped. Meanwhile the ecosystem has moved: GNOME 50 removed the X11 backend from Mutter outright in March 2026, and Wayland is now the default essentially everywhere. Running apps under Xwayland works today and will keep working for years, but you are building on a layer the platform is actively retiring. Budget for that.

Other costs. Encode CPU/GPU per session (get VA-API or NVENC working early, not late); real input latency; per-session memory that makes multi-user density expensive; and a long tail of plumbing — clipboard, drag-and-drop between web and native, file associations, DPI.

Verdict

The only architecture that delivers both halves of what you asked for: a genuine web application, running genuine Linux software. It is also the one that works remotely and multi-user out of the box — which may matter more than the desktop framing.

Option three

Local Shell: HTML as the desktop chrome

boundary at the top, and narrow

Only the panel and the launcher are web; the windows are real

This is the ChromeOS model. You write a Wayland compositor. Your shell UI — panel, launcher, overview, notifications, lock screen chrome — is an HTML document rendered by a WebKitGTK WebView anchored as a layer-shell surface via gtk4-layer-shell and wlr-layer-shell-unstable-v1. Native application windows are composited directly, beneath it, at full speed with zero encode. The webview and the compositor talk over a local IPC socket: window list, focus changes, workspace state, output configuration.

What you build with. wlroots if you want C and the largest body of existing code, or Smithay if you want Rust and vendored dependencies — the latter is what System76 built COSMIC on, and vendoring is a real advantage for the cross-distro problem below. Register the session with a .desktop file in /usr/share/wayland-sessions/ and it appears in GDM, SDDM and greetd like any other DE.

The non-negotiable detail: the screen lock must be implemented in the compositor via ext-session-lock-v1, never as a page in the browser process. If a renderer crash can reveal the desktop, you do not have a lock screen. This is the mistake every web-shell prototype makes.

What it costs. You are now maintaining a compositor, and that is not a side quest — it is multi-year work covering multi-monitor, fractional scaling, per-output DPI, tablet and touch input, drag-and-drop protocols, xdg-shell edge cases, and Xwayland for legacy apps. This is by a wide margin the largest of the three.

Verdict

The only option that is honestly a desktop environment rather than an application. Native performance, real windows, selectable at the login screen. Justified only if shipping an actual DE — not a web product — is the point.

Constraints

Things that will not work, regardless of effort

These are not engineering challenges to be solved with a clever approach. Design around them from the start.

Native windows cannot be embedded in the DOM

Restating it because every web-desktop project tries anyway. You composite outside the browser, or you stream pixels in. There is no third path.

A browser cannot claim global hotkeys

It cannot reserve Super, and it cannot see keys while another app is focused. Compositor-level grabs are the only mechanism — which means Web-Native and Streamed simply do not get real global shortcuts.

A lock screen in a browser process is not a lock screen

Any path where a crashed or killed renderer exposes the session is a security defect, not a bug. Only ext-session-lock-v1 in a compositor is sound.

Accessibility is two disjoint worlds

Native Linux apps speak AT-SPI over D-Bus; your web shell speaks ARIA to the browser's tree. Nothing bridges them for free. If accessibility is a requirement, this is a first-class workstream, not polish.

Clipboard and drag-and-drop need explicit bridging

Web-to-web is fine. Web-to-native, native-to-web, and rich formats (images, file lists, HTML) each need their own plumbing. Xpra forwards clipboard for you; anything else, you write.

Fractional scaling and multi-monitor is where these projects die

Mixed-DPI outputs, per-monitor scale factors, and hotplug are unglamorous and endless. Every web-shell prototype looks great on one 1080p display and falls apart on a laptop plus a 4K external.

Your stated targets

Debian and RHEL/Fedora: what actually differs

The good news is that the base is now genuinely uniform. Both families run systemd and logind, both ship PipeWire, both default to Wayland, and all three common display managers read /usr/share/wayland-sessions/. The base bar in the diagram above is not your problem. Your problem is version skew and security policy.

Concern What is the same What bites you
Library versions Same libraries, same APIs, same protocols. The single biggest cross-distro cost. Fedora tracks upstream closely; Debian stable lags a release or two; RHEL / Rocky lags hard and pushes you to EPEL. wlroots breaks API between releases, so a compositor targeting all three means either version-gated code or vendoring. Rust plus Smithay sidesteps most of this by vendoring crates.
Browser engine WebKitGTK is packaged everywhere. Current on Fedora, older on Debian stable, oldest on RHEL — and the gap is in exactly the CSS and JS features a shell wants. If you need a predictable engine, bundle CEF or ship a Flatpak with a pinned runtime rather than depending on the system WebKit.
Mandatory access control Nothing. This is a genuine fork in the road. FedoraRHEL enforce SELinux; Debian uses AppArmor. A daemon that spawns processes, opens sockets and touches user files will hit both, differently. Write both policies during development. Retrofitting SELinux at the end is a well-known way to lose a month.
Desktop portals Same xdg-desktop-portal D-Bus interfaces on both. A new DE must ship its own .portal file and portals.conf, and set XDG_CURRENT_DESKTOP correctly, or screenshots, screencast and file choosers silently fail. Backend packaging names differ between the families.
Codecs and GPU VA-API and NVENC work on both. Only relevant to the Streamed option, but decisive there. Fedora ships restricted codecs off by default (RPM Fusion); Debian splits free and non-free. Hardware encode paths need per-distro documentation and probably per-distro packages.
Packaging One source tree can produce both. Use nfpm or fpm to emit .deb and .rpm from one spec rather than maintaining debhelper and rpmbuild separately. For server-side pieces, a container with a systemd quadlet unit removes distro packaging from the critical path entirely.
Shortcut

Do not write a privileged daemon

Every web desktop needs the same thing: a way for JavaScript to do system work — call D-Bus, read and write files with real permissions, spawn processes, manage services, read logs — without handing the browser root. Writing that yourself means designing an authentication scheme, a privilege model and an audit story. It is months of work and the most likely place to introduce a serious vulnerability.

Cockpit already is that layer, and it is packaged on both families — RHEL and Fedora ship it as the Web Console, Debian has it in the archive. The architecture is exactly what you'd design: cockpit-ws terminates the WebSocket and authenticates through PAM; it launches cockpit-bridge, which runs as the logged-in user, not root, and speaks a JSON channel protocol over stdio that multiplexes D-Bus calls, file operations and process spawning. Your web code drops into /usr/share/cockpit/ or ~/.local/share/cockpit/ with a manifest.json and gets all of it.

The caveat: it is built for administrative tooling, not for a 60 fps shell. Use it for settings, storage, networking, services, containers and logs. Do not put your window manager's hot path through it.

Recommendation

Build it in three moves, in this order

These are sequential on purpose. Each phase is independently shippable, and each one produces the evidence you need to decide whether the next is worth it. Critically, phase 1's work is not thrown away by phases 2 and 3 — the shell, the window manager and the first-party apps carry forward into all of them.

1

Ship the Web-Native shell

Panel, launcher, workspaces, a JS window manager, and first-party Files, Terminal and Settings apps. System access through cockpit-bridge. Package as one .deb and one .rpm from a single source tree.

Proves the interaction design — the part that has to be good
2

Bolt on Xpra seamless mode

Native apps start appearing as windows in the shell you already built, each one a canvas your existing WM positions and decorates. Add Selkies later if GPU-heavy applications or full-desktop streaming become a requirement.

Proves the hard part, and unlocks the entire Linux app catalogue
3

Decide what this is

By now you know whether users want a remote, multi-user web product — in which case stop here, it is finished and it is good — or a local desktop environment, which means committing to a Smithay compositor and rendering the same shell UI through a layer-shell surface.

The only phase that requires a compositor — defer it until the evidence demands it

If you want my read: phase 2 is the destination for most versions of this idea. It is the only point where the product is both genuinely a web application and genuinely useful for real Linux work, and it reaches users on any machine with a browser — which a local desktop environment, by definition, never does.

Case study

Umbrel shipped this, and declined the window manager

umbrelOS is the closest shipping precedent to what you described, and reading the source settles several open questions. It is the Web-Native option, executed carefully, at roughly 91,000 lines across UI and daemon. The most instructive thing about it is what they chose not to build.

the central finding

There is no windowing code anywhere in it

The entire desktop module is a launcher: wallpaper, dock, a paginated icon grid, widgets, a command palette and context menus. No window frames, no title bars, no resize handles, no z-order management — searching the UI package for draggable windows, title bars or resizable surfaces returns nothing at all. What users read as “a modern desktop” is produced entirely by wallpaper, dock, icon grid and typography.

Apps open in a new browser tab. The launch path is a single window.open(url, '_blank'), and the URL is {protocol}//{hostname}:{app.port} — one port per app on the same host. Not iframes, not a reverse-proxied path. The browser's own tab strip is the window manager.

The cost of that shortcut is visible in the repo: because every app port is a separate origin, they ship an entire second single-page app (packages/ui/app-auth) whose only job is handling login on app origins. A comment in their launch hook shows they have gone back and forth on the approach and consider new-tab-by-default a compromise rather than a design goal.

Layer What Umbrel actually does
Shell UI React SPA on Vite, Tailwind, Radix primitives, TanStack Query, Zustand, tRPC client. ~56,500 lines. Ships first-party Files (CodeMirror editing, PhotoSwipe, video, PDF), Backups, Storage, Settings, a cmdk command palette, a widget system, and a terminal on @xterm/xterm.
System access Not Cockpit. A hand-written daemon, umbreld, ~35,100 lines of TypeScript — Express plus tRPC, JWT and session auth, dockerode for container control, @homebridge/dbus-native on the system bus for systemd disk events, node-pty for the terminal. Its systemd unit sets no User=, so it runs as root.
Applications Docker containers that each already ship their own web UI. There are no native GUI applications in the system, so the native-window problem never arises — which is precisely the limit of the precedent.
Distribution They ship the whole operating system: Debian trixie assembled as a Docker image with pinned apt snapshot dates, converted to a bootable image, with A/B update infrastructure. One distro, one image, total control of the base.
What this changes for RockyWebDE

A convincing desktop does not require windows — that is worth taking seriously before building a window manager. But note the two places Umbrel had it easier than you: every app was already a web app, and they controlled the entire OS image. Your Debian and RHEL requirement is strictly harder than the problem they solved.

And a data point on Cockpit: Umbrel proves it is not required — you can absolutely write your own bridge. It also prices that decision at roughly 35,000 lines of privileged daemon running as root. That is the trade, stated plainly.

the part that matters most

A musl static build dissolves the Debian ↔ RHEL problem

Target x86_64-unknown-linux-musl and you get one statically linked binary that runs unmodified on Debian, RHEL, Fedora, Rocky and Alpine. No glibc version skew, no two build pipelines, no EPEL, no distro-specific runtime dependency to chase. The portability matrix earlier in this document largely stops applying to the daemon.

Two crate choices protect that property, so make them deliberately: use zbus for D-Bus rather than anything binding libdbus, and rustls rather than OpenSSL. Both are pure Rust and keep the static link clean.

Identity

Authenticate through PAM, not against LDAP

This is the decision most self-hosted dashboards get wrong, and it is worth getting right before any code exists.

LDAP gives you an identity. PAM gives you a uid. If your daemon binds to LDAP directly, a login succeeds and you learn that someone is alice — but your terminal has no one to spawn a shell as, and your file manager has no credentials to read /home/alice with. You end up running everything as root and reimplementing permissions in application code, which is how these systems grow a security section they cannot defend.

Authenticate through PAM instead and the whole chain composes, with LDAP plugged in underneath where it belongs:

browser → Rust daemon → pam-client → PAM stack → SSSD → LDAP

Now a successful login yields a real uid, gid and supplementary groups. Drop privileges to that user, spawn the PTY as them, and the kernel enforces file permissions for you — exactly the property that makes Cockpit's bridge safe. Reach for ldap3 only to browse the directory for an admin screen, never for the login path.

running the directory yourself

LLDAP is the lightweight-consistent choice

Written in safe Rust, under 10 MB of memory, SQLite-backed, with its own web admin UI and a GraphQL API. It is packaged for Debian and Ubuntu as well as Fedora and CentOS, and it documents PAM/NSS integration through SSSD or nslcd — which is precisely the chain above. It fits the footprint budget of the rest of this stack.

If the deployment is enterprise RHEL and already has a directory, use it: FreeIPA or 389 Directory Server on that side, SSSD on yours, and nothing about your daemon changes. That is the point of terminating at PAM.

On Better Auth

There is no official LDAP support — only an open discussion, an open issue, and a community credentials plugin you would wire to LDAP yourself, which the project warns is unverified. The harder objection is that it is a TypeScript library: adopting it puts a Node runtime back alongside an 884 KB Rust binary, which gives up the thing you came for.
